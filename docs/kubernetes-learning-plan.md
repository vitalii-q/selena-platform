# План освоения Kubernetes на проекте Selena

## Цель и границы

Цель — получить проверяемый практический базис Kubernetes для начальной позиции Cloud Engineer, работая только локально на MacBook Pro M1 Pro под macOS 12. Основной workload — `users-service`, подключённый к уже работающей Docker PostgreSQL. Второй PostgreSQL сервер в Docker или Kubernetes не создаётся. `hotels-service` остаётся необязательным завершающим упражнением; остальные микросервисы и облачное развёртывание в план не входят.

**Обязательное ограничение для всех этапов:** работать на текущей macOS 12.7.6 и не обновлять macOS. Не предлагать и не выполнять действия, для которых нужна более новая macOS; если отдельное задание плана этому противоречит, соблюдать это ограничение и сообщить о несовместимости.

Каждый подпункт ниже — самостоятельное задание для передачи ИИ. Передавайте их по порядку и по одному. ИИ должен работать в репозитории Selena, читать актуальные файлы перед изменением, сохранять существующие пользовательские изменения и в конце каждого задания сообщать: что изменено, как проверить результат, фактический результат проверки и что осталось. Не считать задачу выполненной только потому, что YAML создан: критерий завершения каждого пункта — воспроизводимая проверка.

**Зафиксированная база плана:** план опирается на проверенное состояние проекта на 20.11.2026: Minikube `selena-local` работает; в Docker уже работает `users-db` на PostgreSQL 15 с host port `9265`; Minikube достигает его; `users-service` требует PostgreSQL до готовности. Второй DB-сервер не нужен. Для изоляции тестовых данных Kubernetes использует отдельную логическую БД и роль внутри существующего PostgreSQL.

**План зафиксирован для этого объёма:** при выполнении подпунктов не переписывать и не перенумеровывать план. В известных местах предусмотрены проверки и fallback. Если проверка не проходит, выполнить диагностику внутри текущего подпункта и остановиться на нём, если указанная проверка всё ещё не проходит; не создавать новые сервисы и не менять архитектуру. Пересмотр плана нужен только при изменении требований пользователя или базовой среды проекта.

## Репозитории, в которых выполнять план

Используем гибридную границу ответственности:

1. **`users-service`** — исходный код, Dockerfile и Helm chart/Kubernetes-манифесты Users в `users-service/k8s/`. Это основной репозиторий учебного этапа.
2. **`hotels-service`** — исходный код, Dockerfile и Helm chart/Kubernetes-манифесты Hotels в `hotels-service/k8s/`. Он используется только для дополнительного этапа закрепления.
3. **`infrastructure`** — Terraform и облачные ресурсы/настройки кластера (например, будущий EKS, сеть и IAM). В этом плане инфраструктурный репозиторий не изменяется: локальный кластер создаётся отдельным учебным инструментом, AWS не используется.

Таким образом, каждый сервис можно собирать и развёртывать отдельно из собственного репозитория, а общая облачная инфраструктура остаётся отдельным слоем. Общий chart сервиса не должен зависеть от AWS-specific API: локальные различия передаются отдельным values-файлом; облачные интеграции и настройки будут добавляться только в будущем инфраструктурном слое. Не использовать локальные `hostPath`, `NodePort`, жёстко заданные IP, облачные аннотации или имена StorageClass в переносимой конфигурации приложения. В этот план не входят создание AWS-кластера, настройка EKS/IAM/сети и перенос в AWS.

## Базовые возможности Kubernetes, которые демонстрирует проект

1. **Поддержание заданного числа Pods:** Deployment пересоздаёт удалённый Pod; проверка — удалить Pod и наблюдать восстановление ReplicaSet.
2. **Стабильный адрес приложения:** ClusterIP Service скрывает меняющиеся IP Pods; проверка — DNS-запрос из временного Pod и запросы к Service.
3. **Конфигурация вне образа:** ConfigMap и Secret передают настройки; проверка — проверить окружение/поведение приложения, не раскрывая значение пароля.
4. **Постоянное хранилище:** временный PVC сохраняет marker после пересоздания диагностического Pod; приложение продолжает использовать существующий Docker PostgreSQL.
5. **Контроль здоровья:** probes влияют на готовность и перезапуск; проверка — статус Ready и endpoints Service при нездоровом Pod.
6. **Масштабирование приложения:** число реплик можно менять; проверка — сравнить состояние и одинаковый короткий GET-нагрузочный тест при 1 и 2 репликах.
7. **Входной HTTP-маршрут:** Ingress Controller направляет локальный запрос к Service; проверка — curl с тестовым host/path. Если локальная среда не поддерживает Ingress, использовать port-forward и указать ограничение.
8. **Повторяемые установки и обновления:** Helm хранит параметры и историю release; проверка — lint/template, install/upgrade/rollback и health после каждого перехода.

## Что сознательно не входит в базовый объём

1. AWS/EKS и любые облачные ресурсы.
2. Все остальные микросервисы Selena, кроме `users-service` и учебного `hotels-service`.
3. HPA и автоматическое масштабирование: для них нужны рабочие метрики и осознанные пороги; для базовой демонстрации достаточно ручного изменения реплик.
4. Перенос или дублирование PostgreSQL в Kubernetes, production database clustering, backups и HA: Users использует уже имеющийся Docker PostgreSQL; Kubernetes PVC изучается отдельно на временном диагностическом workload.
5. Большие нагрузочные тесты: локальная машина показывает поведение только своей конфигурации и не является прогнозом облачной мощности.
